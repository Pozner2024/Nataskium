# 0017. Контракт типа задания и реестр типов

- **Статус:** Принято
- **Дата:** 2026-11-26

## Контекст
Типов заданий уже три (викторина — [ADR-0012](0012-quiz-timer.md), сопоставление — [ADR-0013](0013-matching-activity.md),
«да/нет» — [ADR-0016](0016-true-false-activity.md)), в планах — до 30. Каждый новый тип повторяет один и тот же набор кода,
а в нескольких местах общий код ветвится по типу вручную:

- **Сервер.** У типа своя папка в `features/` (5 use-case'ов, репозиторий, маршруты `/api/<тип>`) и свои строки в `app.ts`.
  `getPlayActivity` ищет `shareToken` по типам последовательными индексными запросами: на 30 типах это до 30 запросов
  на каждое открытие игры. `takeLibraryQuiz`, `toActivityThumbnail` и фильтры репозиториев ветвятся по `type`.
- **Общий пакет.** `ACTIVITY_KINDS`, объединения схем ответа игры и превью, CHECK в миграциях — списки правятся по отдельности.
- **Сайт.** `PlayPage` (switch и `RULES_KEYS`), `COUNT_KEYS` (в двух местах), `EDIT_PATHS` (в двух), `REMOVE_APIS`, превью и миниатюра.

Часть этих таблиц — `Record<ActivityType, …>`, и забытый тип там уже не пройдёт проверку типов. **Молча** ломаются ветки
«по умолчанию»: в `takeLibraryQuiz` после проверок сопоставления и «да/нет» любой другой тип считается викториной;
так же в `toActivityThumbnail`, в `ActivityThumbnail.vue` (`v-else` — сопоставление) и в `PlayPage` (запасной `{ kind: 'quiz' }`).
Новый тип там тихо превратится в викторину.

Что уже общее и используем: все типы лежат в одной таблице `quizzes`, `shareToken` уникален на всю таблицу,
у типов одинаковые правила (оценка по проценту, результаты не сохраняются, публикация в библиотеку).

## Решение
Принимаем принцип: **тип описывается модулем по общему интерфейсу, общий код берёт модуль из реестра по `type`,
а не ветвится вручную.** Вводим постепенно, три шага, каждый — отдельный план. Объединение всех маршрутов игры и
кабинета в общие откладываем (см. «Отложено»).

**Шаг 0. Исчерпывающие ветвления.** В местах с веткой по умолчанию (`takeLibraryQuiz`, `toActivityThumbnail`,
`ActivityThumbnail.vue`, `PlayPage`) — `switch` по `type` с вспомогательной функцией `assertNever`: новый тип без обработки
не соберётся. Без смены архитектуры, дёшево, закрывает тихие ошибки сразу.

**Шаг 1. Общие таблицы вместо копий (сайт и общий пакет).**
- Пути редактора по типу — `editActivityPath(kind, id)` в `packages/shared/routes` рядом с `newActivityPath`:
  заменяет `EDIT_PATHS` ×2 и `takenEditPath` (у пакета нет ограничений ФСД).
- Ключи подсчёта (`COUNT_KEYS` ×2) и правил игры (`RULES_KEYS`) — реестр данных в `entities/activity`.
- `REMOVE_APIS` остаётся в слое виджетов: он ссылается на API трёх сущностей, а сущность не импортирует сущность.
- Объединения схем в `packages/shared` остаются явными (из реестра их не генерируем: так уже получался цикл импортов,
  см. `playActivity.ts`) и проверяются `satisfies Record<ActivityKind, …>`.

**Шаг 2. Сервер: модуль типа на чтении.**
- Модуль типа (слой application): `toPlayResponse` (без правильных ответов), `toThumbnail`, `toCopy` («Взять себе»), счётчик элементов.
- Одна загрузка по `shareToken`: репозиторий отдаёт строку любого типа вместе с `type`, дальше работает модуль
  (вместо перебора типов в `getPlayActivity`). `check` и `finish` уже делают один типизированный запрос каждый.
- Маршруты **по типам остаются**, но собираются из модуля (`makeActivityRoutes(module)`): адреса, лимит размера тела
  (у викторин отдельный из-за картинок), порядок «лимитер → тело (400) → номер (404)» и одинаковый 404 не меняются.
  Исчезает дублирование в `app.ts`, а не контракты.
- Пилот — «да/нет», самый маленький тип: на нём проверяем интерфейс модуля, потом переносим остальные два.
  Четвёртый тип пишется уже по контракту.

**Контрактные тесты.** Один набор проверок запускается для каждого модуля: ответ игры не содержит правильных ответов,
неизвестный и чужой токен дают один и тот же 404, `finish` с неверной длиной ответа — 400. Новый тип проходит его автоматически.
Один общий тест проверяет, что у каждого ключа есть CHECK в БД, запись в реестрах и локали ×4.

## Отложено
Единые маршруты игры (`/check`, `/finish` для любого типа) и единый `/api/activities` для кабинета — отдельным ADR,
когда появятся типы 4–5 и станет видно, что у типов действительно общее (то же основание, что в [ADR-0016](0016-true-false-activity.md)).
Что придётся решить тогда, чтобы не потерять сегодняшние гарантии:
- лимит размера тела: у `/api/quizzes` он больше из-за картинок, а транзакция с привязкой картинок есть только у викторины;
- порядок проверок [ADR-0019](0019-library-opens-game.md): тело (400) идёт до номера (404); при загрузке до проверки тела он
  изменится, тело придётся различать по `type` внутри самого запроса;
- у сопоставления нет `check`, у остальных он только при `showAnswers`: общий маршрут должен отвечать тем же «нет такого маршрута» (404).

Сейчас публичного запуска нет, поэтому менять публичные адреса API дёшево; к запуску решение лучше принять.

## Последствия
- Шаги 0–1 дёшевы и сразу закрывают тихие ошибки; шаг 2 убирает перебор типов на открытии игры и дублирование в `app.ts`.
- Новый тип: модуль, записи в реестрах, переводы, редактор и игра. Забытое место не собирается или падает контрактным тестом.
- Цена: рефакторинг трёх работающих типов; под риском игра и «Взять себе». Интеграционные тесты игры, библиотеки и кабинета
  остаются зелёными на каждом шаге.
- **Безопасность.** Модуль возвращает ответ игры, поэтому утечка правильных ответов в одном модуле затронет один тип, а не все;
  защита — контрактные тесты и ревью каждого шага.
- Данные не меняются: таблица, колонка `questions` (jsonb) и CHECK по типам остаются.
- Остаётся открытым: интерфейс модуля уточняется на пилоте («да/нет»); решения из раздела «Отложено».

## Отвергнутые варианты
- **Оставить как есть и вести чек-лист.** Дёшево, но тихие ветки по умолчанию превращают забытый тип в викторину.
- **Один общий роутер `/api/activities` и общие маршруты игры сразу.** Ломает лимит тела викторин, порядок проверок
  ADR-0019 и «нет такого маршрута» для `check`; на трёх типах не видно, что в них действительно общее. Отложено.
- **Отдельная таблица на тип.** Не нужна: токен уникален на всю таблицу, общий список и библиотека работают без объединений.
- **Вертикальные модули «всё про тип в одной папке» (новый слой ФСД).** Противоречит ФСД из CLAUDE.md и требует переноса
  десятков файлов сразу; реестры дают тот же эффект без смены слоёв.
- **Динамическая загрузка типов как плагинов.** Лишняя сложность: типы пишем мы сами и тестируем вместе с остальным кодом.
