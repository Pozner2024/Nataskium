# 0016. Тип задания «Да/нет»

- **Статус:** Предложено
- **Дата:** 2026-11-19

## Контекст
Нужна игра «да/нет»: ученик читает утверждение и отвечает «Да» или «Нет». Это третий тип задания рядом с викториной
([ADR-0012](0012-quiz-timer.md) про таймер) и сопоставлением ([ADR-0013](0013-matching-activity.md)). В планах не менее
10 типов, поэтому новый тип должен ложиться в уже принятую модель без переделки старых.
Действуют принятые правила: оценка только по проценту правильных ответов, результаты не сохраняются, публикация в
библиотеку по [ADR-0002](0002-library-auto-publish.md), [ADR-0004](0004-library-existing-and-deleted.md) и
[ADR-0005](0005-library-take-copies.md).

## Решение
Третий тип `truefalse` по образцу сопоставления ([ADR-0013](0013-matching-activity.md)).
- **Одна таблица `quizzes`**, колонка `type` получает значение `truefalse`. Утверждения хранятся в существующей
  колонке `questions` (jsonb) массивом `{ statement, answer }`, `answer` — boolean. Одна ссылка `/play/<shareToken>`
  для всех типов.
- **Правила содержимого** (Zod при сохранении): 2–30 утверждений, текст не длиннее 200 символов, повторы запрещены без
  учёта регистра, пробелов и формы Unicode (`matchingKey`, сообщение схемы `Duplicate text`).
- **CHECK** в БД (миграция `20261119120000_add_truefalse_type`): расширенный `quizzes_type_check`
  (`quiz`, `matching`, `truefalse`) и новый `quizzes_truefalse_items_check`: у `truefalse` в `questions` массив из 2–30 элементов.
  Границы дублируют `MIN/MAX_TRUE_FALSE_ITEMS`.
- **Кабинет:** `/api/true-false` (`POST /`, `GET|PATCH|DELETE /:id`), те же правила владельца и 404, что у `/api/quizzes`
  и `/api/matchings`; id задания другого типа тоже даёт 404. Список — общий `GET /api/quizzes`. Лимит 100 заданий и
  лимитеры кабинета общие со всеми типами.
- **Игра:**
  - `GET /api/play/:token` отдаёт `type: 'truefalse'` и `statements[]` в порядке учителя, без ответов.
  - `POST /api/play/:token/true-false/check` с телом `{ version, index, answer }` — только при `showAnswers`,
    иначе 404, как будто маршрута нет. Лимитер `check`. Индекс вне диапазона даёт 400.
  - `POST /api/play/:token/true-false/finish` с телом `{ version, answers: (boolean | null)[] }`; `null` — «не отвечено»
    (0 баллов, [ADR-0012](0012-quiz-timer.md)). Длина строго равна числу утверждений, устаревшая `version` даёт 409.
    Лимитер `finish`. Поле `review` (`{ correct, answer }[]`) приходит только при `showAnswers`, иначе его нет вовсе.
- **Оценка** — `summarizeQuiz`: верный ответ даёт `QUESTION_POINTS`, неверный или `null` 0.
- **Библиотека:** карточка показывает утверждения без ответов; «Взять себе» копирует ответы в непубличную копию
  ([ADR-0005](0005-library-take-copies.md)).
- Часть про экран игры (`widgets/true-false-play`) ждёт `player-embed`
  ([ADR-0014](0014-play-inside-intro-player.md)) и в этот ADR не входит.

## Последствия
- **У «да/нет» всего два варианта ответа, поэтому ответы подобрать проще, чем у сопоставления.** При `showAnswers = false`
  можно отправлять частичные ответы (`null` у остальных утверждений), и по проценту выяснять одно утверждение за запрос.
  На всё задание нужно N+1 ≤ 31 вызов `finish` (базовый запрос и по одному на утверждение). Это меньше лимита `finish`
  120/мин на IP. Это расширение риска, принятого в [ADR-0013](0013-matching-activity.md); защиту не добавляем
  (решение пользователя).
- `check` доступен только при `showAnswers = true`, когда ответы и так показываются, — новой утечки он не создаёт.
- Карточка библиотеки не раскрывает больше, чем игра: ни там, ни там ответов нет.
- **Миграция высокого риска.** Down-миграций у Prisma нет; ручной откат и правило отката кода — в заголовке миграции.
  Пока в базе есть строки `truefalse`, откатывать код нельзя: старый код парсит любую строку схемой викторины и падает.
  Перед откатом такие строки скрывают (`deleted_at = now()`, `is_public = false`), предварительно сохранив список id.
- Название колонки `questions` по-прежнему вводит в заблуждение (см. [ADR-0013](0013-matching-activity.md)).
- Следующие типы лягут в ту же таблицу тем же приёмом.
- Персональных данных и новых зависимостей не добавляется. Данные учеников не хранятся.

## Отвергнутые варианты
- **B. Режим викторины «да/нет».** Редактор викторины неудобен для списка утверждений, у задания нет собственной
  идентичности (тип, карточка, название в интерфейсе).
- **C. Сначала обобщить бэкенд в `/api/activities`.** Отложено: на трёх типах видно не всё общее. Обобщение — отдельный
  шаг (будущий ADR 0017), когда станет ясно, что у типов общего.
