# 0013. Тип задания «Сопоставление»

- **Статус:** Предложено
- **Дата:** 2026-11-16

## Контекст
Нужен второй тип задания после викторины: ученик сопоставляет пары «слово ↔ определение» (только текст).
Действуют принятые правила: оценка только по проценту правильных ответов, результаты не сохраняются,
публикация в библиотеку по [ADR-0002](0002-library-auto-publish.md), [ADR-0004](0004-library-existing-and-deleted.md)
и [ADR-0005](0005-library-take-copies.md), таймер по [ADR-0012](0012-quiz-timer.md).

Главная трудность — протокол. У викторины клиент перемешивает варианты и отправляет исходный индекс.
В сопоставлении индекс и есть правильная связь, поэтому этот приём не подходит: ни `GET /api/play/:token`,
ни публичная карточка библиотеки не должны выдавать связь слова с определением ни порядком, ни id.

## Решение
- **Одна таблица `quizzes`** и новая колонка `type` (`quiz | matching`, по умолчанию `quiz`). Пары хранятся
  в существующей колонке `questions` (jsonb) массивом `{ term, definition }`. Колонку не переименовываем.
- Два CHECK, они дублируют константы Zod:
  - `quizzes_type_check`: `type IN ('quiz', 'matching')`;
  - `quizzes_matching_pairs_check`: у `matching` в `questions` массив из 2–10 элементов.
- Каждый существующий запрос к `quizzes`, который парсит строку схемой викторины, фильтрует по `type = 'quiz'`.
  Список кабинета, список библиотеки, `countByTeacher` и purge намеренно работают без фильтра.
- **Лимит 100 заданий — общий** на все типы (`MAX_ACTIVITIES_PER_TEACHER`). Суточный лимитер создания и лимитеры
  кабинета — те же экземпляры для обоих типов.
- **Правила пар** (Zod при сохранении):
  - 2–10 пар; слово не длиннее 60 символов, определение не длиннее 200;
  - обе стороны обязательны;
  - в тексте те же запреты символов, что у викторины (`safeText`);
  - слова уникальны внутри задания, определения тоже. Сравнение по нормализованному ключу: NFC, trim,
    схлопнутые пробелы, без учёта регистра.
- Подписи в интерфейсе: «Слово / Определение».
- **Игра:**
  - `GET /api/play/:token` отдаёт `type`. Для сопоставления в ответе `definitions[]` в порядке учителя
    и `terms[]`; слова сервер перемешивает (CSPRNG Fisher–Yates) при каждом запросе. Ответ собирается
    явно, без `pairs` и без id.
  - Клиент определения не перемешивает: номер определения — порядок учителя. Перемешаны только слова, и только сервером.
  - `POST /api/play/:token/matching/finish` с телом `{ version, answers: (string | null)[] }`.
    Элемент `answers[i]` — текст слова для определения `i`; `null` означает «не отвечено» (0 баллов, ADR-0012).
    У викторины «не отвечено» по ADR-0012 — пустой массив `[]`; расхождение осознанное: у сопоставления
    отдельный путь `/matching/finish` со своей схемой.
    Длина должна быть ровно равна числу пар. Неизвестное слово и одно слово дважды дают 400.
    Устаревшая `version` даёт 409.
  - Токен задания другого типа на чужом маршруте даёт 404, как неизвестный токен.
  - `/check` для сопоставления нет. Правильные пары приходят в ответе `finish` полем `review` и только
    при `showAnswers = true`; иначе поля нет вовсе.
  - Лимитеры — существующие `get` и `finish` из `PLAY_LIMITS`, новых нет.
- **Оценка** — `summarizeQuiz` без изменений: верная пара даёт 60 баллов, неверная или пустая 0, `partialCount = 0`.
- Таймер работает по ADR-0012 без изменений.
- **Библиотека:**
  - публикация сразу при создании ([ADR-0002](0002-library-auto-publish.md)), удаление по
    [ADR-0004](0004-library-existing-and-deleted.md), копия «Взять себе» с `is_public = false`
    ([ADR-0005](0005-library-take-copies.md));
  - карточка показывает **все** определения в порядке учителя и **все** слова, перемешанные сервером
    (не больше 10 пар), без ограничения `LIBRARY_PREVIEW_QUESTIONS`. Это ровно те же данные, что отдаёт
    `GET /api/play/:token`;
  - адрес карточки для обоих типов остаётся `/library/quiz/<номер>-<slug>`: адреса зафиксированы
    до SEO-этапа ([ADR-0011](0011-seo-last.md)).
- Название типа в интерфейсе — «Сопоставление».
- Главный путь ученика — перетаскивание слова из лотка, прилипающего к верху экрана, на определение. Своя реализация
  на Pointer Events, без новых зависимостей. Тап (слово, затем определение) — запасной путь, он же путь клавиатуры
  и скринридера.

## Последствия
- **Подобрать ответы у сопоставления дешевле, чем у викторины.** При `showAnswers = false` можно отправлять
  частичные ответы (`null` у остальных пар) и по проценту проверять одну пару за запрос.
  На всё задание нужно до ~n² запросов `finish`: до 100 запросов при 10 парах, то есть подбор
  укладывается в одну минуту с одного IP (лимит `finish` — 120/мин/IP). Это расширение уже принятого риска подбора ответов перепрохождениями. Защиту не добавляем.
- При `showAnswers = true` вызов `finish` с пустыми ответами раскрывает пары до прохождения.
  Это та же допустимая возможность, что вызов `check` у викторины без ответа.
- Карточка библиотеки не раскрывает больше, чем игра: те же определения и те же перемешанные слова,
  что любой получает по ссылке `/play/<shareToken>`. Дополнительной утечки сверх play нет.
- **Миграция высокого риска.** Down-миграций у Prisma нет. В заголовке миграции — ручной откат:
  `DROP CONSTRAINT` обоих CHECK, `DROP COLUMN "type"` и удаление записи миграции из `_prisma_migrations`.
  Перед применением на dev-БД — бэкап.
- **Правило отката.** Пока в базе есть строки `type = 'matching'`, откатывать код нельзя: старый код парсит
  любую строку схемой викторины и отвечает 500 в кабинете, библиотеке и игре. Поэтому перед откатом кода
  такие строки сначала скрывают:
  - `is_public = false` убирает задание только из библиотеки; кабинет и игра старого кода по-прежнему падают
    на строках `matching`. Поэтому для отката кода обязателен один шаг:
    `UPDATE quizzes SET deleted_at = now(), is_public = false WHERE type = 'matching' AND deleted_at IS NULL`;
  - перед этим сохранить список id затронутых строк (SELECT или дамп). Тогда после повторного выката их можно
    вернуть (`deleted_at = NULL`) в пределах 30 дней, до purge. Без списка вернуть задания учителей нельзя,
    после purge они удалены окончательно.
  Порядок выката: миграция, затем API и web вместе. Правило дублируется в заголовке миграции.
- **Название колонки `questions` вводит в заблуждение:** у сопоставления в ней лежат пары. Переименование
  (например, в `content`) отложено: оно затронуло бы сырой SQL и типы Prisma. До тех пор формат колонки
  для каждого типа описан в комментарии `schema.prisma`.
- Миграция аддитивная: существующие строки получают `type = 'quiz'`, на PG 18 таблица не перезаписывается.
- Главный риск единой таблицы — пропущенный `type`-фильтр и 500 на строке другого типа. Его закрывают
  реестр запросов в плане и тесты изоляции типов.
- Следующие типы («пропуски», «картинки») лягут в ту же таблицу без переделки викторин.
- Персональных данных и новых зависимостей не добавляется. Данные учеников не хранятся.

## Отвергнутые варианты
- Отдельная таблица `matchings`: двойной `public_number`, UNION в списке библиотеки, вручную общий лимит,
  дублирование purge, каскада и индексов.
- Непрозрачные id пар, сохранённые в jsonb: меняют форму данных, усложняют копирование, остаётся риск утечки связи.
- Id или перестановка из HMAC (`shareToken`, `version`, индекс): нужен секрет, ошибка генерации даёт утечку,
  выигрыша перед ответом по тексту нет.
- Перемешивание обеих колонок только на клиенте: порядок в ответе `GET` выдал бы связь.
- `/check` по каждой паре: лишний маршрут, а показ ответов в итоге закрывает ту же потребность одним запросом.
- Общий `/finish` с union-телом: пустой `[]` подходит обоим типам, валидация неоднозначна.
- Отдельный лимит 100 на каждый тип: фактически 100 × число типов, а лимит защищает диск и purge.
- Первые 5 пар в карточке библиотеки (`LIBRARY_PREVIEW_QUESTIONS`): при n > 5 набор показанных слов
  раскрывает, какие слова относятся к показанным определениям, а какие — к скрытым. Все пары дают ровно
  то же, что игра, и подсказки не добавляют.
- Библиотека drag-n-drop: новая зависимость; HTML5 DnD не работает на тач-экранах.
