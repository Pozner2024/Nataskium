# Nataskium — Claude Instructions

## Проект

Платформа обучающих игр и интерактивных заданий для учителей — аналог Wordwall и Blooket. Проект интернациональный.
Полная архитектура: `docs/architecture.md`.

### Ключевые продуктовые решения

- **Оценивание** — главное отличие от аналогов. Учитель сам решает, ставить ли оценку за задание
- Оценка считается **только по проценту правильных ответов** (скорость и очки не влияют)
- Шкалы: 10-балльная, 5-балльная (русская), американская (A–F); учитель может создать **свою шкалу**. Новые шкалы добавляются без переделки остального кода
- Один сценарий: учитель создаёт задание и делится ссылкой, ученик проходит игру. Режимы «живая игра в классе» и «домашнее задание» — не в первой версии, возможно, не будут никогда
- Ученики заходят **по ссылке** — без регистрации. Аккаунт только у учителя
- **Результаты не сохраняются** (первая версия): сервер проверяет ответы и возвращает процент и оценку, ученик видит их на своём экране; учитель в кабинете результатов не видит

## Правила бэкенда (`apps/api`, будет создано)

### Clean Architecture (упрощённая) — 3 слоя

Работаем с Prisma-моделями напрямую. Три слоя:

- **Application** — бизнес-логика (use-cases), по одному файлу на операцию (`login.ts`, `register.ts`)
- **Infrastructure** — работа с БД (репозитории), Prisma-операции
- **Presentation** — HTTP маршруты (Hono)
- `app.ts` — единственный файл, который импортирует и Application, и Infrastructure (composition root)

## Правила фронтенда (`apps/web`, будет создано)

### ФСД: слои и правила импортов

Слои сверху вниз: `pages` → `widgets` → `features` → `entities` → `shared`.
Импорт только сверху вниз. Виджеты не импортируют виджеты.
Всегда через `index.ts`, deep imports запрещены.

### ФСД + Nuxt

Схема как в NatsDoll:

- Код ФСД лежит в `src/`: `src/pages`, `src/widgets`, `src/features`, `src/entities`, `src/shared`. Алиас `@` → `src` (в `nuxt.config.ts`)
- `app/pages/` — только роутинг Nuxt. Файл тонкий: импорт страницы из `src/pages` + `definePageMeta`, без логики:

```vue
<template>
  <CartPage />
</template>

<script setup lang="ts">
import CartPage from '@/pages/CartPage.vue'

definePageMeta({ name: 'cart' })
</script>
```

- Страницы ФСД — `src/pages/{Name}Page.vue`, собираются из виджетов
- Папки `app/components/` нет, автоимпорт компонентов не используется — компоненты импортируются явно через `index.ts` слайса
- Правило `no-restricted-imports` в ESLint запрещает deep imports

**Структура слайса (widgets / features / entities):**

```
{layer}/{sliceName}/
├── {SliceName}.vue          главный компонент (всегда)
├── components/              (опционально, если подкомпонентов 2+)
├── use{SliceName}.ts        (опционально)
├── {sliceName}Api.ts        (опционально)
├── store.ts                 (опционально)
├── types.ts                 (опционально, если тип в 2+ файлах)
├── {sliceName}.test.ts      unit-тесты рядом с кодом
└── index.ts                 ОБЯЗАТЕЛЕН
```

Исключение: если имя главного компонента конфликтует со страницей из `src/pages`, допускается суффикс `Widget` (`CartPageWidget.vue`, `ProductPageWidget.vue`).

**shared:**
```
shared/
├── ui/        примитивы (AppButton, AppLogo, etc)
├── lib/       утилиты
└── index.ts
```

### Типы в файлах

- Тип используется в **одном файле** → пишем его в самом файле
- Тип используется в **двух и более файлах** → в `types.ts`
- Экспортируем через `index.ts` для публичного API

### CSS — BEM в `<style scoped>`

Стили пишутся в `<style scoped lang="scss">` блоке компонента, используется BEM-нотация.
Отдельные `.scss` файлы только если стили переиспользуются в нескольких компонентах.


**Цвета с прозрачностью:** всегда `rgb(r g b / alpha)`, никогда `rgba(r, g, b, alpha)`.
**Статичные цвета:** hex. **Прозрачные:** через CSS-каналы `rgb(var(--x) / alpha)`.
**Z-index:** каскадом через `calc(var(--предыдущий) + 1)`, все значения в `global.scss` (блок `--z-*`).
**Адаптация:** только через миксины `@include tablet { ... }` и `@include desktop { ... }` из `@/assets/styles/breakpoints.module`. Запрещены хардкод-значения типа `@media (width >= 768px)`. В начале `<style scoped lang="scss">` подключать через `@use '@/assets/styles/breakpoints.module' as *;`.

## Стиль кода

- **Простота** — пиши минимальный код, который решает задачу; простой и читаемый код лучше умного и сложного
- **Вложенность** — используй early return вместо вложенных `if`; максимум 2–3 уровня
- **Единообразие** — для схожих задач используй одинаковые подходы (если в проекте уже есть паттерн — следуй ему)
- **Одна ответственность** — функция делает одно; если в названии есть "и" — это два метода
- **Async/await** — не `.then()` цепочки
- **Нет магических чисел** — только именованные константы (`REFRESH_TOKEN_TTL_MS`, не `604800000`)
- **TypeScript** — запрет `any`; на системных границах (HTTP, внешние API) использовать `unknown` с последующей валидацией через Zod
- **Комментарии** — только там, где они действительно необходимы, т.е. где без пояснения код непонятен (неочевидная причина, обходной путь, бизнес-правило). Не пересказывать комментарием то, что и так видно из кода

## Безопасность — приоритет №1

Безопасность сервиса и данных пользователей важнее скорости разработки и удобства. Среди пользователей — дети, поэтому данные учеников защищаются особенно строго. При сомнении выбирать более безопасный вариант и сообщать пользователю о риске.

### Сторонние библиотеки

- **Перед добавлением любой зависимости** проверить её на известные уязвимости (`npm audit`, GitHub Advisory Database), дату последнего релиза, активность поддержки и популярность. Заброшенные и малоизвестные пакеты не брать; о найденных рисках сообщать до установки
- Не добавлять библиотеку ради того, что решается несколькими строками своего кода
- `package-lock.json` всегда в репозитории; в Docker и CI — только `npm ci`
- `npm audit` перед каждым коммитом: уязвимости **high / critical блокируют коммит**, moderate — сообщить пользователю
- **Принятые исключения** (одобрены пользователем 2026-10-20): `braces` и `node-forge` (high) — транзитивно через `nuxt`/`nitropack`, исправленных версий нет, в production-сборку (`.output`) не попадают; `esbuild` (low) — только dev-сервер на Windows. Новые уязвимости в этих же пакетах или в коде, попадающем в `.output`, по-прежнему блокируют коммит. При каждом обновлении Nuxt проверять, не вышли ли исправления, и убирать исключение
- При обновлении зависимостей читать changelog на breaking changes и security-фиксы

### Данные пользователей

- **Минимум данных:** данные учеников не сохраняются вообще; не собирать email, фамилию, возраст, геолокацию учеников
- Пароли — только хэш (argon2id); токены и секреты никогда не попадают в логи, ответы API и git
- Секреты только в переменных окружения; `.env` в `.gitignore`
- Учитель видит **только свои** задания и шкалы — проверка владельца в каждом use-case
- Все входные данные валидируются Zod на сервере; клиентской валидации не доверять
- Логи без персональных данных (имена учеников, email, IP — только если необходимо и с обоснованием)
- Удаление аккаунта учителя должно удалять его персональные данные (GDPR)

### Защита сервиса

- Только HTTPS; cookies `httpOnly`, `Secure`, `SameSite`
- Security-заголовки (`secureHeaders` в Hono) и CSP
- CORS — только whitelist доменов, не `*`
- Rate limiting на вход, регистрацию, сброс пароля и все публичные эндпоинты учеников
- Загружаемые файлы: проверка типа и размера на сервере, случайные имена
- Ссылки на задания — случайный `shareToken`, не последовательный id
- Никакого `v-html` с пользовательским контентом

## Working Style

- Сначала ПЛАН, потом код — для задач, затрагивающих 2+ файла или архитектурный слой
- Маленькие дифы: изменил файл → убедился что работает → следующий файл
- Исследование кодовой базы (Glob, Grep, Read) — делай сам для простых поисков; делегируй `planner`-агенту для анализа архитектуры и планирования

## Перед началом работы

- **Явные предположения** — если задача неоднозначна, сформулируй предположения вслух и спроси до начала работы, не угадывай
- **Критерий успеха** — определи конкретную проверку до написания кода ("работает" = что именно?)
- **Хирургические изменения** — при редактировании трогай только необходимое; не рефакторь соседний код, который не сломан; не удаляй импорты/функции, которые не ты сделал лишними

## Agents (`.claude/agents/`)

- `planner` — перед любой задачей, затрагивающей 2+ файла, новую фичу или архитектурное решение
- `tester` — после изменений кода; агент сам определяет нужный scope тестов
- `code-reviewer` — перед каждым коммитом; critical/high findings блокируют коммит
- `fullstack-developer` — фича целиком через все слои (Prisma → Hono → Nuxt)
- `widget-developer` — новые виджеты и блоки фронтенда по паттернам проекта
- `vue-expert` — сложные задачи Vue/Nuxt: реактивность, composables, Pinia, SSR
- `ui-designer` — визуальный дизайн компонентов, бренд, доступность
